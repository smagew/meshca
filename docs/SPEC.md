# meshca: спецификация

Версия 0.3, 2026-11-24. Статус: этапы 1 (сбор) и 2 (разбор) реализованы, остальное в плане.

## 1. Назначение

Собственная база всех пакетов MeshCore, которые слышит наш observer, и аналитика поверх неё:

1. **Активность узлов**: кто сколько отправляет, какие типы пакетов, как часто, в какое время.
2. **Ретрансляция**: какие узлы чаще всего пересылают пакеты и какую долю трафика несут.
3. **Закономерности**: классы узлов, периодичность, структура сети, диалоги, аномалии, потери.

### Входит в проект
- приём копии пакетов observer'а, долговременное хранение в сыром виде;
- разбор пакетов, справочник узлов;
- расчёты из раздела 7;
- интерфейс: панели Grafana и собственное веб-приложение (раздел 8).

### Не входит
- изменение observer'а, его прошивки или его отправки в LetsMesh;
- отправка чего-либо в эфир (проект только слушает);
- расшифровка личных сообщений (невозможна для пассивного наблюдателя);
- картина всей сети: мы видим только то, что слышно с одной точки.

## 2. Термины

| Термин | Значение |
|---|---|
| observer | Узел-наблюдатель: LoRa-нода на USB и сервис `meshcore-packet-capture` (v2.2.1), публикует всё услышанное в MQTT |
| приём | Один факт приёма пакета observer'ом (одна запись MQTT). Один пакет обычно даёт несколько приёмов |
| пакет | Уникальное содержимое, ключ — `hash` (SHA-256 от типа и содержимого, без пути). Одинаков у всех копий |
| путь | Список ретрансляторов, через которые прошёл пакет. Каждый дописывает свой префикс |
| префикс | Первые 1–3 байта публичного ключа узла. Однобайтовый префикс неоднозначен |
| последний узел пути | Ретранслятор, которого observer услышал напрямую |
| узел | Устройство сети с публичным ключом: клиент, ретранслятор, сервер комнат, датчик |

## 3. Источник данных

### 3.1 Что отдаёт observer
Тема MQTT `meshcore/{IATA}/{PUBLIC_KEY}/packets`, одно сообщение JSON на приём. Все значения строки:

`origin`, `origin_id`, `timestamp` (ISO, UTC), `type`, `direction`, `time`, `date`, `len`, `packet_type`,
`route`, `payload_len`, `raw` (весь пакет в hex), `SNR`, `RSSI`, `hash`.

Поле `path` на верхнем уровне есть только у пакетов с маршрутом `D`. Для остальных путь берём из `raw`.
Поле `payload_len` у observer'а равно полной длине пакета (как `len`), длину содержимого считаем сами.
В одной сети встречаются пакеты и с однобайтовыми, и с двухбайтовыми префиксами пути.

Тема `.../status`: состояние observer'а (модель, прошивка, параметры радио, статистика) раз в 5 минут.

### 3.2 Формат пакета (для разбора `raw`)
`заголовок(1) | коды транспорта(4, не всегда) | длина пути(1) | путь | содержимое`

- заголовок: биты 0–1 тип маршрута, 2–5 тип содержимого, 6–7 версия;
- тип маршрута: 0 TRANSPORT_FLOOD, 1 FLOOD, 2 DIRECT, 3 TRANSPORT_DIRECT; коды транспорта есть при 0 и 3;
- длина пути: биты 0–5 число узлов, биты 6–7 размер префикса минус один (1, 2 или 3 байта);
- типы содержимого: 0 REQ, 1 RESPONSE, 2 TXT_MSG, 3 ACK, 4 ADVERT, 5 GRP_TXT, 6 GRP_DATA, 7 ANON_REQ,
  8 PATH, 9 TRACE, 10 MULTIPART, 11 CONTROL, 15 RAW_CUSTOM.

### 3.3 Что видно без ключей
| Тип | Что читаем |
|---|---|
| ADVERT | Всё: публичный ключ, время узла, роль, координаты (если есть), имя |
| GRP_TXT, GRP_DATA | Однобайтовый хеш канала. С ключом канала (Public и хештег-каналы) — время, имя отправителя, текст |
| REQ, RESPONSE, TXT_MSG, PATH | Только однобайтовые хеши получателя и отправителя |
| ANON_REQ | Хеш получателя и полный ключ отправителя |
| ACK | Только контрольная сумма, без адресов |
| CONTROL | Обычно открыто: ответы на обнаружение соседей |

### 3.4 Исходные цифры (журнал observer'а, 18–22.11.2026, 4,9 суток)
- 22 867 приёмов, 12 356 уникальных пакетов; около 4700 приёмов в сутки;
- 85% пакетов приходят ровно в двух копиях: observer слышит два ретранслятора (уровни около −83 и −91 дБм);
- доли типов: ADVERT 21,8%, GRP_TXT 21,8%, REQ 17,0%, ANON_REQ 10,2%, TXT_MSG 9,9%, GRP_DATA 8,8%,
  PATH 6,9%, RESPONSE 2,7%, ACK 0,4%, CONTROL 0,3%.

## 4. Требование №1: не нарушить observer

- **O-1.** Единственное изменение на стороне observer'а — один новый файл настроек с блоком `[[broker]]`
  и один перезапуск сервиса. Существующие файлы не редактируются. Декодирование в observer'е не включается.
- **O-2.** Публикация в наш брокер идёт с qos 0. Недоступность нашего брокера не должна влиять на захват
  и на отправку в LetsMesh. По коду observer'а это так (брокеры независимы, сервис считается неисправным
  только при отказе всех брокеров); подтверждено испытаниями этапа 1 ([DEPLOY.md](DEPLOY.md), раздел 3).
  Найденное ограничение observer'а: к брокеру, который не ответил при его старте, он больше не подключается
  до перезапуска сервиса. На LetsMesh это не влияет; для нас это повод для проверки связи (раздел 9).
- **O-3.** Откат: удалить этот файл, перезапустить сервис. Инструкция: [DEPLOY.md](DEPLOY.md).
- **O-4.** На машину observer'а не ставится ничего из этого проекта.

## 5. Архитектура

```
LoRa-нода → observer ──→ LetsMesh (без изменений)
                    └──→ mosquitto ─→ collector ─→ PostgreSQL ←─ worker (разбор и расчёты)
                                                        ↑
                                              Grafana, api + web
```

Всё, кроме observer'а, — один стек Docker Compose на отдельной машине в той же локальной сети.

| Контейнер | Назначение | Этап |
|---|---|---|
| `mosquitto` | Брокер только для этого проекта. Пользователь `observer` только публикует, `collector` только читает; анонимного доступа нет | 1 |
| `collector` | Подписка на темы observer'а, запись каждого сообщения без изменений (`raw_reception`, `observer_message`) | 1 |
| `migrate` | Применяет миграции схемы и завершается | 1 |
| `postgres` | Хранилище. Данные на отдельном томе | 1 |
| `worker` | Разбор `raw`, справочник узлов, расчёты по расписанию | 2 |
| `grafana` | Панели и оповещения | 3 |
| `api`, `web` | Собственный интерфейс | 8 |

Принципы:
- **Сырые данные неизменяемы.** `raw_reception` только дополняется. Всё остальное можно удалить и пересчитать из неё.
- **Версия разборщика** записывается в каждую производную строку: при изменении протокола пересчитываем.
- **Время** хранится в UTC, в интерфейсе показывается местное.
- **Сборщик не разбирает пакеты.** Он должен быть настолько простым, чтобы не падать на незнакомых данных.

Технологии: Python 3.12 (paho-mqtt, psycopg, pandas, networkx, scipy, scikit-learn, ruptures),
PostgreSQL актуальной стабильной версии, Grafana. Разбор содержимого опирается на логику
`payload_decode.py` из `agessaman/meshcore-packet-capture` (лицензия MIT, с указанием источника).

## 6. Модель данных

### Сырой слой
| Таблица | Поля | Смысл |
|---|---|---|
| `raw_reception` | `id`, `ingested_at`, `topic`, `payload jsonb`, `payload_text` | Сообщение темы `packets` как есть (`payload_text` — если это не JSON) |
| `observer_message` | `id`, `ingested_at`, `topic`, `kind`, `retained`, `payload jsonb`, `payload_text` | Все остальные сообщения observer'а: `status`, `neighbors` и любые новые |

### Разобранный слой
Строит `worker` из сырого слоя. Ключи, хеши и префиксы — текст в hex нижним регистром; `hash` пакета — как у observer'а, верхним.

| Таблица | Поля | Смысл |
|---|---|---|
| `reception` | `id` (= `raw_reception.id`), `received_at`, `observer_id`, `packet_hash`, `route_type`, `snr`, `rssi`, `packet_len`, `path text[]`, `hop_count`, `prefix_size`, `last_hop`, `transport_codes`, `hash_ok`, `decoder_version` | Один приём. `last_hop` — ретранслятор, которого observer услышал напрямую (только для маршрутов FLOOD; пусто, если услышан сам отправитель) |
| `packet` | `hash` PK, `first_seen`, `last_seen`, `payload_type`, `payload_len`, `payload bytea`, `reception_count` | Уникальный пакет |
| `advert` | `packet_hash`, `pubkey`, `advert_time`, `role`, `lat`, `lon`, `name`, `signature_ok` | Разобранное объявление; подпись Ed25519 проверяется |
| `node` | `pubkey` PK, `name`, `role`, `lat`, `lon`, `first_seen`, `last_seen`, `advert_count` | Справочник узлов, только по объявлениям с верной подписью |
| `node_history` | `pubkey`, `changed_at`, `field`, `old`, `new` | Смена имени, роли, координат |
| `channel` | `name`, `key`, `hash`, `source`, `added_at` | Каналы с известным ключом: Public, из настроек, из упоминаний `#имя` |
| `channel_message` | `packet_hash`, `payload_type`, `channel_hash`, `channel`, `decrypted`, `sender_name`, `text`, `text_len`, `msg_time`, `data_type`, `ciphertext_len`, `text_removed` | Сообщения каналов (GRP_TXT и GRP_DATA) |
| `direct_packet` | `packet_hash`, `dst_hash`, `src_hash` | REQ, RESPONSE, TXT_MSG, PATH |
| `anon_request` | `packet_hash`, `dst_hash`, `sender_pubkey` | ANON_REQ |
| `decode_error` | `raw_id`, `error`, `decoder_version` | Сырая запись, которую не удалось разобрать, и причина |
| `worker_state` | `key`, `value jsonb` | Позиция разбора, версия разборщика, состояние проверок |
| `monitor_event` | `id`, `at`, `name`, `state`, `message`, `notified` | Смена состояния проверок сбора (раздел 9) |

При смене версии разборщика `worker` очищает разобранный слой и строит его заново из `raw_reception`.

### Аналитический слой
| Таблица | Поля | Смысл |
|---|---|---|
| `hop_resolution` | `reception_id`, `position`, `prefix`, `pubkey`, `probability`, `method_version` | Какой узел стоит за префиксом, с вероятностью |
| `origin_resolution` | `packet_hash`, `pubkey`, `probability`, `method`, `method_version` | Кто отправитель пакета |
| `edge_daily` | `day`, `from_pubkey`, `to_pubkey`, `packets`, `weight` | Связи «B услышал A» |
| `node_features` | `pubkey`, `window`, `features jsonb`, `computed_at` | Признаки узла за окно |
| `node_class` | `pubkey`, `window`, `class`, `explanation` | Класс узла |
| `finding` | `id`, `kind`, `subject`, `window`, `score`, `p_value`, `evidence jsonb`, `status` | Найденная закономерность со ссылками на пакеты |
| `anomaly` | `id`, `kind`, `subject`, `detected_at`, `severity`, `details jsonb`, `evidence jsonb`, `state` | Сработавшая аномалия |

Объём: около 4700 строк `raw_reception` в сутки, 1,7 млн в год. Секционирование не требуется.

## 7. Расчёты

Для каждого: вход, метод, выход, минимум данных, проверка.

### 7.1 Активность узлов (вопрос 1)
- **Вход:** `packet`, `origin_resolution`, `advert`, `channel_message`.
- **Метод:** подсчёт уникальных пакетов по отправителю, типу, часу, дню; интервалы между пакетами.
- **Выход:** таблица узлов: пакетов за период, доли типов, медианный интервал, часы активности.
- **Оговорка:** надёжная атрибуция есть для ADVERT, ANON_REQ и сообщений каналов. Для личных сообщений — с вероятностью (7.3).
- **Проверка:** сверка 5–10 узлов с LetsMesh.

### 7.2 Ретрансляция (вопрос 2)
- **Вход:** `reception.path`, `hop_resolution`.
- **Метод:** сколько уникальных пакетов прошло через узел, на какой позиции пути, какая доля от всех.
- **Выход:** рейтинг ретрансляторов, динамика по дням, сравнение двух наших соседей (кто приносит пакет первым).
- **Оговорка:** все пути заканчиваются на двух соседях observer'а; рейтинг — «с нашей точки».

### 7.3 Определение узла по префиксу (основа для 7.2, 7.4, 7.7)
- **Вход:** префиксы путей, однобайтовые хеши личных сообщений, справочник узлов.
- **Метод:**
  1. однозначные префиксы (подходит один известный ретранслятор) дают достоверные связи;
  2. для неоднозначных — вероятность кандидата по трём признакам: активен ли сейчас, встречался ли рядом
     с соседями по пути, правдоподобно ли расстояние по координатам;
  3. повторять до стабилизации оценок;
  4. отправителя анонимного пакета привязывать по «отпечатку пути»: маршруту, которым приходят его объявления.
- **Выход:** `hop_resolution`, `origin_resolution` с вероятностями. Ниже порога — «не определён».
- **Минимум данных:** 2 недели.
- **Проверка:** на пакетах с 2–3-байтовыми префиксами (там ответ известен) усечь префикс до одного байта
  и измерить долю верных определений. Целевое значение фиксируется после первого замера.

### 7.4 Топология
- **Метод:** направленный граф из соседних узлов пути. Для каждого отправителя — узлы, через которые
  проходят все его пути до нас (анализ доминаторов). Разнообразие путей: число маршрутов и энтропия.
  Сообщества (Leiden) — обзорно.
- **Выход:** `edge_daily`; список критичных узлов с перечнем тех, кого отрежет их отказ; узлы с единственным маршрутом.
- **Проверка:** сравнение с графом соседей в LetsMesh; неправдоподобно длинные связи возвращаются в 7.3 как ошибки.

### 7.5 Временные закономерности
- **Рваность:** коэффициент вариации интервалов, B = (σ − μ)/(σ + μ).
- **Периодичность:** тест Рэлея на окружности длиной T с перебором T.
- **Профиль:** вектор из 168 часов недели; типовые ритмы через разложение NMF матрицы «узел × час».
- **Минимум данных:** 30 событий на узел, 2–4 недели.
- **Проверка:** перестановочный тест (перемешать времена внутри узла), подтверждение на второй половине данных.

### 7.6 Классы узлов
- **Признаки:** доли типов, частота, рваность, сила периодичности, доля ночной активности, число пересылок
  до нас, разнообразие путей, заявленная роль.
- **Метод:** иерархическая кластеризация; каждому классу — словесное объяснение по ведущим признакам.
- **Выход:** `node_class`.
- **Проверка:** устойчивость классов между соседними окнами; ручной просмотр 3–5 узлов каждого класса.

### 7.7 Кто с кем общается
- **Личные сообщения:** сессии по парам хешей и паузам; запрос и ответ — по обратной паре в пределах секунд;
  время отклика; доставка — сопоставление TXT_MSG и ACK по времени (оценка).
- **Каналы:** отправитель из текста; граф ответов по близости во времени и упоминаниям.
- **Сценарии:** матрица переходов между типами пакетов в сессии против случайной.
- **Оговорка:** результат вероятностный, зависит от 7.3.

### 7.8 Аномалии
| Аномалия | Метод |
|---|---|
| Всплеск или провал трафика (сеть, узел) | Медиана и устойчивый разброс для часа недели; сдвиги уровня — CUSUM, PELT |
| Узел замолчал | Порог по 99-му процентилю его собственных пауз |
| Смена маршрута | Дивергенция Йенсена — Шеннона между распределениями путей по неделям |
| Дрейф сигнала соседа | Контрольные карты SNR и RSSI |
| Новый узел, смена имени, то же имя с новым ключом | Сравнение со справочником |
| Сбитые часы узла | Время в объявлении против времени приёма |
| Один узел занимает непропорциональную долю эфира | Доля времени передачи |

- **Минимум данных:** 4 недели.
- **Проверка:** прогон на истории, подсчёт срабатываний в сутки; цель — не более нескольких в день.

### 7.9 Потери и эфир
- **Потери по объявлениям:** 1 − получено/ожидалось для узлов с устойчивым периодом.
- **Потери по двум соседям:** оценка Линкольна — Петерсена (нижняя граница: соседи не независимы).
- **Занятость эфира:** время передачи по формуле LoRa из длины пакета и параметров радио (из темы `status`).

### 7.10 Правила достоверности (для всех находок)
- находка записывается в `finding` только со ссылкой на пакеты, на которых она видна;
- проверка на второй половине данных и перестановочный тест;
- поправка на множественные проверки (Бенджамини — Хохберг);
- контрольные данные: собственные узлы владельца отправляют заранее известные пакеты.

## 8. Интерфейс

### 8.1 Grafana (первый слой)
| Панель | Содержание |
|---|---|
| Обзор сети | Пакеты по часам, типы, активные узлы, новые узлы, состояние сбора |
| Узлы | Таблица «кто сколько шлёт» с фильтрами по роли, типу, периоду |
| Ретрансляторы | Рейтинг, доля трафика, динамика, сравнение двух соседей |
| Радио | SNR и RSSI по соседям, занятость эфира, потери |
| Ритм | Карта «час × день недели» по сети и по выбранному узлу |
| Карта | Узлы по координатам |
| Аномалии | Лента срабатываний, оповещения |

### 8.2 Собственное веб-приложение (второй слой)
| Экран | Содержание |
|---|---|
| Карточка узла | Лента активности, типы, ритм, класс с объяснением, маршруты до нас, собеседники, история изменений |
| Граф сети | Интерактивный граф, подсветка критичных узлов, фильтр по времени, достоверность связей |
| Находки | Список закономерностей; у каждой — описание, оценка достоверности, пакеты-доказательства |
| Аномалии | Разбор «почему сработало», отметка «ложная тревога» для подстройки порогов |
| Пакет | Все приёмы пакета, пути, разобранное содержимое |

Требования: доступ только из локальной сети; интерфейс на русском; везде видно, где факт, а где оценка с вероятностью.

## 9. Нефункциональные требования

- **Docker:** весь проект разворачивается одной командой `docker compose up -d`; на машине вне Docker ничего не ставится.
- **Ресурсы:** ограничения памяти на каждый контейнер; PostgreSQL настроен с учётом того, что машина занята другим приложением.
- **Диск:** данные на отдельном томе (20 ГБ, с возможностью расширения), не на корневом разделе:
  если корневой раздел заполнится из-за другого приложения, база не пострадает.
- **Хранение:** сырые данные бессрочно. Исключение: расшифрованные тексты каналов хранятся 1 месяц;
  одновременно из сырой записи вырезается зашифрованное содержимое этих сообщений (иначе текст можно
  расшифровать заново). Заголовок, путь, уровень сигнала и `hash` остаются.
- **Бэкап:** пока не делается (решение владельца, 2026-11-22). Следствие: отказ диска означает потерю
  всей накопленной истории, восстановить её неоткуда. Вернуться к вопросу после вехи A.
- **Публичный репозиторий:** в файлах, сообщениях коммитов и обсуждениях нет адресов и имён машин,
  ключей, личных данных владельца и захваченных данных.
- **Контроль сбора:** две проверки в `worker`. «Связь с observer'ом»: нет сообщения о состоянии (оно приходит
  раз в 5 минут) дольше 15 минут — observer не подключён к нашему брокеру, нужен перезапуск его сервиса.
  «Пакеты»: связь есть, но приёмов нет дольше 30 минут. Смена состояния пишется в `monitor_event` и в журнал,
  а также отправляется в Telegram и/или на произвольный адрес запросом POST, если они заданы в настройках.
- **Секреты:** пароли брокера и базы, ключи каналов — только в `.env` вне репозитория. В репозитории `.env.example`.
- **Данные вне репозитория:** захваченные пакеты, тексты каналов и дампы в git не попадают.
- **Язык:** код, комментарии, журналы — английский; документация и интерфейс — русский.

## 10. Критерии приёмки

| Этап | Критерий |
|---|---|
| 1. Сбор | За сутки число строк `raw_reception` совпадает с числом приёмов в журнале observer'а (расхождение до 1%). При остановке нашего брокера на 10 минут observer продолжает захват и отправку в LetsMesh. Observer запускается при выключенном нашем брокере |
| 2. Разбор | 100% строк разобраны либо помечены причиной отказа. `hash`, вычисленный разборщиком, совпадает с `hash` observer'а. Путь есть у всех пакетов с ненулевым числом узлов |
| 3. Вопросы 1 и 2 | Панели «Узлы» и «Ретрансляторы» работают; цифры по 5–10 узлам сходятся с LetsMesh |
| 4. Определение узлов | Измерена точность на усечённых префиксах; доля неопределённых узлов показана в интерфейсе |
| 5. Топология | Список критичных узлов; ни одной связи длиннее правдоподобной дальности без пометки |
| 6. Ритмы и классы | У каждого класса есть объяснение; классы устойчивы между двумя соседними окнами |
| 7. Аномалии, потери | Оповещения приходят; ложных срабатываний не больше нескольких в день |
| 8. Веб-приложение | Все экраны из 8.2 работают на реальных данных |

## 11. Открытые вопросы

Открытых вопросов нет.

### Решено
| Дата | Вопрос | Решение |
|---|---|---|
| 2026-11-22 | Срок хранения текстов каналов | 1 месяц. После этого текст удаляется, остаются отправитель, время, канал и длина сообщения |
| 2026-11-22 | Какие каналы расшифровывать | Все, для которых известен ключ: Public и хештег-каналы. Ключ хештег-канала выводится из его имени, поэтому список имён пополняется автоматически из упоминаний `#имя` в уже расшифрованных текстах. Каналы с секретным ключом расшифровать нельзя |
| 2026-11-22 | Узлы владельца (контрольные данные) | Три узла. Их имена задаются в локальных настройках (`OWN_NODES` в `.env`) и в репозиторий не попадают: объявления узлов содержат координаты |
| 2026-11-22 | Второй observer | Пока нет. Все выводы о топологии — с одной точки |
| 2026-11-22 | CoreScope | Пока не нужен |
| 2026-11-22 | Репозиторий публичный или закрытый | Публичный |
| 2026-11-22 | Бэкап базы | Пока не делается |
| 2026-11-22 | Место под данные | Отдельный том 20 ГБ |
